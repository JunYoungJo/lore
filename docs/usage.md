# Using Lore

[About Lore and getting started](../README.md) · [Multiple PCs](multiplatform.md) · [Sync review](sync-review.md)

The app is `lore`, the CLI is `lore-cli`, and the app identifier is `io.github.junyoungjo.lore`. The commands and paths below use these names.

On first launch, follow the setup guide. On an existing install you can reopen it with **Settings → Advanced → Run setup guide again**. The guide provides a built-in terminal for installing tools and signing in, the memory folder, MCP, rule, skill and hook connections, and indexing. For managing connections and what is kept, see the [setup guide](setup.md). The CLI connect/disconnect commands below manage hooks only.

## How a note comes to be

Lore does not write notes on its own judgment. The session you work in marks what is to be remembered, you decide, and only what you approved reaches the notes. The design and its reasons are in [Recording through candidates](design/candidates.md).

1. **Mark.** With each prompt, a hook tells the session how to mark a decision you made, a correction to how it works, or a lesson the work established, at the moment it happens. The session runs `lore-cli mark <decision|correction|lesson> "<sentences>" --by <user|agent> --said "<your words>"`: the statement, whose it is (yours, or the agent's proposal or finding), and the words of yours it rests on. When the session knows that this changes what a note says, or that what a note says no longer applies (it read the note with qmd), it names the note: `--updates <note>` or `--retires <note>`, with `--quote "<the note's words it changes or ends>"`. The command writes nothing. It prints one line with the mark's id, which ends up in the session file, where Lore reads it later. When you change your mind later in the session, the session marks the new version with `--replaces <id>`; a mark that was wrong it withdraws with `lore-cli mark cancel <id>`. Only what the session marks becomes a candidate: Lore does not look for anything in the conversation afterwards.
2. **Prepare.** When a session ends or is about to be compacted, Lore reads the marks made since the last time. The program applies what they replace and withdraw, and checks the words of yours that a mark quotes against what you said in the session. A mark that names a note is taken as it is when the note is in `common/` or the project's folder and the quoted words are in it word for word. For the other marks the recording model says how each stands to the notes that exist: nothing on it yet, a note already says it, a note says something it changes, or a note is about something it ends. It also says whether a candidate that already waits states it. The program checks every quoted passage against the note. A step whose marks all name their notes, or that has no mark, calls no model.
3. **Review.** **Needs attention** shows "N candidates to review", and a notification says so when a session ends. The Candidates window lists them by session. You go through them, reword if needed, decide approve, discard or later, and apply the decisions.
4. **Apply.** The recording model turns the candidates you approved into note changes: new notes, edits of existing notes, removals. The program accepts them only when every change rests on a candidate you approved. The notes are committed and indexed, and the window shows which sentence went into which note.

Candidates stay on this PC, in the app's database. Only notes are in the memory folder, and only the memory folder is synced.

## Registering hooks

In the popover's settings screen, "Connections" shows a combined connection status for MCP, instructions, skills and hooks for each of Claude Code and Codex ("Connected", "Needs repair", "Not connected"). Connecting, repairing and disconnecting happen in the integrations window opened by "Manage connections". Its left-hand list shows Codex, Claude Code, the memory folder, the search index and tools with their status, and for each item it shows what is wrong and why (for example, a hook runs Lore from a different location) along with a button to fix it. To connect or disconnect hooks only, use `lore-cli.exe connect <claude|codex>` and `disconnect <claude|codex>`. The app does not change global settings files until you click. Disconnecting removes only the lore hooks, and also removes an event entry created during connection if it is left empty. Uninstalling the Windows NSIS build makes the uninstaller disconnect the lore hooks for Claude and Codex (not when reinstalling for an update). On macOS and Linux, disconnect the hooks before removing the app.

- Claude: adds `SessionEnd`, `PreCompact` and `UserPromptSubmit` entries to `hooks` in `~/.claude/settings.json`, and allows the mark command in `permissions.allow` there: `Bash(<lore-cli> mark *)` and, on Windows, `PowerShell(<lore-cli> mark *)`.
- Codex: adds `SessionEnd`, `PreCompact` and `UserPromptSubmit` entries to `hooks` in `~/.codex/hooks.json`, and writes `~/.codex/rules/lore.rules`, a file of Lore's own with one `prefix_rule` that allows `<lore-cli> mark`. The new hooks run only after you mark them as trusted with `/hooks` in Codex.
- Without the allow rules, a session asks you before each mark, and Claude Code's auto mode may refuse it. Disconnecting removes the two Claude rules and the Codex rules file along with the hooks.
- The pre-compaction hook queues the conversation so far when it grows long enough to trigger automatic (or manual) compaction, even if the session has not ended. Parts already read are not read again; reading continues at the next compaction or when the session ends.
- The prompt hook adds a short instruction to each prompt you send: how to mark something worth remembering (see [How a note comes to be](#how-a-note-comes-to-be)). It does not look at what you wrote, reads no settings and stores nothing. The mark command it names is the same `lore-cli`, which the connection allows as described above.
- A connection that lacks one of the three hooks or the allow rules is shown as "Needs repair" (or "Not connected" if MCP, instructions and skills are also missing). Reapplying the connection in the integrations window or running `lore-cli connect` adds only what is missing.

The executable is `lore-cli.exe` on Windows and `lore-cli` on macOS and Linux. Unix hook paths are quoted so they run literally even if they contain shell special characters.

Existing hooks and other settings keys are left as they are, in the same order, and new entries are appended to the end of the array. Older lore hooks that point to a different install location are switched to the new path. The file before the change is kept in the same folder as `<file>.lore-backup-<timestamp>`. The recording model process gets `LORE_RECORDER=1`, so its own session is neither queued nor told to mark.

## Data locations

`%LOCALAPPDATA%\io.github.junyoungjo.lore` below is the app data location on Windows. On macOS it is `~/Library/Application Support/io.github.junyoungjo.lore`, and on Linux `${XDG_DATA_HOME:-~/.local/share}/io.github.junyoungjo.lore`. `LORE_HOME` overrides the data folder for both the app and the CLI.

The default for a new memory repository is `~/Documents/lore-memory`; a location already set in `settings.json` is kept. `D:\doc\lore-memory` below is an example of a location used on Windows. qmd configuration, index and cache are created per PC under `qmd/<memory path hash>/` in the app data, not in the memory repository. During initial setup, run `index` and set the environment variables of the qmd MCP connection to the paths `doctor` shows.

| Path | Contents |
|---|---|
| `%LOCALAPPDATA%\io.github.junyoungjo.lore\settings.json` | Settings. The app checks this file every 2 seconds and applies manual edits without a restart. The first-launch time (`since`) is the cutoff before which the manual `scan` command skips sessions. |
| `%LOCALAPPDATA%\io.github.junyoungjo.lore\state.sqlite` | Job queue, processing positions, failure counts, recent activity, and the candidates with what became of them. A candidate you approved, discarded or that a note already covered is removed 30 days after it was found. |
| `%LOCALAPPDATA%\io.github.junyoungjo.lore\reviews\` | Model inputs and responses for the last 50 runs |
| `D:\doc\lore-memory\projects\<project>\`, `common\` | Memory notes (indexed by qmd). Nothing else is written into the memory folder: no copy of a conversation is kept, and a note carries the quotations it rests on. |

## Processing rules

- **Recording CLIs:** **Settings → Recording** lists Claude and Codex in the order Lore tries them, each with its own model and effort. The first one reads every session and writes every batch you approved. Turn the second one on to have it take over when the first cannot run, for example at its usage limit, after its login expired, or when it times out; **Use first** swaps the order. An answer the program rejected is not a reason to switch: the same model is asked again with the reason. The sync comparison and the cleanup use the same order. A CLI that is not found on this PC cannot be turned on; **Set up…** opens the tools page.
- **What a candidate is:** One mark of the session: one to three sentences and at most 600 characters, that can be understood without the conversation, in the session's own wording. It has a kind: a **decision** you made, a **correction** to how the assistant works, or a **lesson** the work established. It says whose it is: yours (`--by user`), or the agent's proposal you approved or the agent's finding (`--by agent`). A decision or a correction carries your words (`--said`), and the command refuses one without them; a correction is always yours. The program keeps a quoted word of yours only when it finds it in something you said in the session before the mark, at least ten characters long or the whole of what you said; words it cannot find are not shown as yours. For a mark of the agent, the window and the note's sources show the agent's sentence as the agent's words, next to your approval.
- **A note the session names:** With `--updates <note>` or `--retires <note>` and `--quote`, the session says itself which note the mark changes or ends. The note may be given relative to the memory folder (`projects/<project>/alerts.md`), as qmd lists it (`project-<project>/alerts.md`), or by its full path. The program checks that it is a note of `common/` or of the project and that every quoted passage is in it word for word; the window then shows "Edits a note" or "Deletes a note" with that note and those passages, and approving it edits or ends that note. A note that is not there, or that lacks the quoted words, is not used: the mark is then compared with the notes like any other.
- **How a candidate stands to the notes:** For the marks that name no note, one model call per step looks up the notes about each mark itself: it searches the notes of `common/` and the project's folder with qmd (this PC's index of the memory folder) and with the file tools, and reads them, read-only. It is given the marks and the candidates that wait, not the conversation, and it does not change what a mark says. The model runs with your own CLI setup and global instructions, but without hooks, plugins, skills, your MCP servers or sub-agents; see [Recording through candidates](design/candidates.md#what-the-model-is-given). The model answers with one of four: no note on it (`new`), a note already says it (`same`), a note says something this changes (`differs`), or a note is about something this ends (`obsolete`). For the last three it names the note and copies the passages it means; the program checks that they are in the note word for word. A candidate that is `same` is not listed. The window only counts it under its session ("2 statements already in your notes were left out"), and **Show** lists them with the note that holds each. A mark that a waiting candidate already states is not listed again. The instructions are in `crates/core/src/prepare-prompt.md`. Which notes the model read is kept in `events.jsonl` in the step's folder under `reviews\`.
- **Replacing and withdrawing a mark:** A mark that replaces or withdraws one made earlier in the same session takes the earlier one out of the list while it waits, also when a compaction already offered it. Once you approved or discarded the earlier one, your decision stands: a replacement is then a candidate of its own, which the model relates to the note the earlier one became, and a withdrawal changes nothing.
- **The Candidates window:** Opened by **Review** next to "N candidates to review", by **Open** in **Settings → Candidates → Candidates and what was written** (there whether or not anything waits), from a "Candidates" row of the recent activity while some of its candidates wait, or by **Show in Candidates** in the note card of an "n notes updated" row, which opens the Written tab on that batch. The left side lists the waiting candidates by session. Every row has the same height: an icon for what you decided, two lines of the sentence, and one line with its kind in color and, in grey, "All projects", "Edits a note", "Deletes a note" (in red), "Edited", or "Auto-approves in N days" when automatic approval is on. The header counts how many are decided. The right side shows the chosen candidate in three parts: the sentence to remember, the quoted words with who said them and when, and what approving does. **Edit** (or `E`, or a click on the sentence) rewords it: `Enter` saves, `Shift+Enter` starts a new line, `Esc` cancels, and leaving the field saves. What approving does says first whether the candidate adds to your notes, edits a note or deletes a note. A new statement offers two choices, this project or all projects, each saying who reads it (`1` and `2` choose them); an edit or a deletion shows the note's title, its path and the copied passages. Clicking the note opens it. The window never shows a diff of a note.
- **Approving and discarding:** You go through the candidates one at a time. At the bottom of the right side, **Discard** (`D`), **Later** (`L`) and **Approve and next** (`A`) decide the candidate in view and move on to the next undecided one; `↑`/`↓` move without deciding, and **Undo** (`U`) takes a decision back. Nothing is sent until you press **Apply** at the bottom of the window, which names what it sends ("Apply: approve 5, discard 2"); until then every decision can be changed. Later and undecided candidates keep waiting. Every candidate starts undecided. **Discard N undecided candidates** and **Approve N undecided candidates** decide the undecided ones together, but leave out one that arrived while the window was open until you have looked at it, so nothing you have not seen is approved or discarded. A discarded candidate does not come back.
- **What was written (Written tab):** The window has two tabs, **To review** (the candidates above, with how many wait) and **Written**. Written lists the approved batches by the day they were written, newest first: those being written or waiting to be tried again, those that could not be written, and those written. Choosing one shows its summary and, for each note, whether it was created, edited or removed and which sentences went into it; clicking a note opens it. A batch that could not be written offers **Try again** and **Put back in the list**, which returns its candidates to To review. The tab counts the batches that are being written or failed, in red when one failed. When Apply leaves nothing to review, the window switches to Written. Written batches stay listed for 30 days and are then removed from this list; **Clear** removes them at once after asking. Neither touches a batch still being written or one that failed, and neither changes the notes: what was written stays in the notes and their commits.
- **Writing approved candidates:** The candidates you approved are grouped by project, and each group is written in one request. The model gets the approved sentences with their quotations, the notes the review showed, and further notes found by search, and returns new notes, edits and removals. The program accepts the answer only when every change and every removal names the approved candidates it rests on, every approved candidate went into at least one change, a `differs` or `obsolete` candidate changed the note it was shown with, a removed note is one an approved `obsolete` candidate showed you, and every statement went into a note of the folder it applies to: `common/` for all projects, `projects/<project>/` otherwise. A statement about one project is never added to a shared note, where every other project would read it. A note you were not shown may be edited so that it agrees with what you approved, and the result lists it; it is never removed. The instructions are in `crates/core/src/integrate-prompt.md`.
- **What was written:** After an approval the right side of the window shows each batch: the notes it created, edited or removed, with the sentences that went into each, and a one-sentence summary. **Written into your notes** at the bottom of the list returns to it. The recent activity shows the same batch as "n notes updated".
- **A batch that could not be written:** The notes are unchanged. The batch is retried like a session (see Failures). When it gives up, **Needs attention** shows "1 approved batch not written" and the window offers **Try again** and **Put back in the list**, which returns its candidates to the waiting list as they were. A batch that had begun to write when it gave up first takes back what it wrote, so a failed batch never leaves part of itself in the notes. Once every note of a batch is written, the batch is no longer one that can fail: if only the search index could not be refreshed, the result says so and Lore keeps trying.
- **If Lore stops while it writes:** The plan of a batch is stored before its first note is written. On the next start the batch is finished from that plan without asking the model again. Until then no sync and no cleanup runs, so notes that are half written are neither shared nor rewritten.
- **Automatic approval:** **Settings → Candidates → Approve automatically** is off by default: a candidate waits until you approve or discard it. When it is on, a candidate that has waited the number of days set below it (3 by default, 1 to 365) is approved as it stands, and written like any other; a decision you made in the window but did not apply does not hold it back. The rows then show "Auto-approves in N days". The days count from the later of two times: when the candidate entered the list, and when you turned automatic approval on. Turning it on therefore approves nothing at once, however long the candidates have waited, and a candidate you put back in the list gets its full time again. Notes changed by an automatic approval wait in the review window; notes changed by your own approval count as reviewed.
- **When you are told:** A notification says how many candidates a session left once the session has ended and all of it is read. A compaction in the middle of a session offers candidates without a notification; they are in **Needs attention** right away and are counted in the notification when the session ends.
- **Failures:** A failed job is postponed to a scheduled next attempt, so it does not block other jobs. Run failures and timeouts are retried up to 8 times, starting at 1 minute and doubling up to a 1-hour interval; model response validation failures are retried up to 3 times, each time with the reason the last answer was rejected. Failures that would give the same result on retry, such as a missing source or a change in the already-processed beginning, go straight to `failed`. For a `failed` session, open the queue screen with "View" under "Needs attention" on the status screen, then use "Retry" to requeue it or "Skip" to move past it. Approved batches are retried the same way.
- **Discarding:** Clicking "Skip" on the queue screen and confirming once more skips what the session file holds after the failed job's processing position and moves the processing position to its end; the job is marked done, and what the session adds later is read at the next compaction or when it ends. If the source file is missing, the processed beginning has changed, or the source JSON is broken so its end cannot be found, the session is marked `skipped` and is not read further. If the error might go away on retry, such as failing to decompress a compressed source, nothing is changed and the error is shown. This cannot be undone.
- **Queue screen:** Clicking the waiting line under the status card (for example "2 sessions waiting · 1 retrying") or "View" under "Needs attention" opens the queue screen, which lists the session being read and the waiting, retry-pending and failed ones with project, session ID and status, and scrolls to the matching group. The waiting line appears only when there are waiting or retry-pending jobs. For jobs that have not started yet, the project is shown by reading the session ID and working folder from the start of the source. The job being read is not counted as waiting.
- **Needs attention:** Collects only the things to act on in the status screen, one per line: unconnected hooks, candidates to review, approved batches that could not be written, notes to review, sessions that could not be read, and memory not yet shared with other PCs. If there is nothing to do, this section is hidden. States that pause the work, such as an open review window, are shown in the status card at the top.
- **Long sessions:** One step reads everything the session file holds since the last step, however long. No part of the conversation is sent to a model, so its length sets no limit.
- **Language:** A candidate is in the language the session marked it in, and a note made from it is written in that language; an existing note keeps its language when it is edited. File names and the `## Sources` heading the program adds are English.
- **Sessions that are not read:** Codex subagent sessions (marked `subagent` in the session file), sessions in Claude's `subagents` folder, and sessions run outside a git repository are marked `skipped`.
- **Input sent by agents:** Fixed-format messages sent by Orca or other agents are marked `agent` per input. These are inputs that start with "You are working inside Orca", "You are a dispatched worker", "Please carry out this task from my Orca coordinator", "Continue work from the prior Orca session", "The prior provider session is read-only context", "Original agent: ", or "Another Claude session sent a message", or whose first line is "You have N orchestration message(s)". If every input in the new segment is `agent` (or, for a segment with only replies and no input, if the previous input was `agent`), the segment is passed over with its marks: what a session marks while it works for another agent is not yours. If there is at least one other input, its marks are prepared. An `agent` input does not count as your words: a mark's quotation is kept only when it is found in an input of yours.
- **Messages sent mid-task:** Messages the user sends while the assistant is working are stored in the Claude session file as `attachment` records (`queued_command`, `origin.kind: "human"`). The app reads them as user turns at that position. Subagent reports that arrive in the same format (`origin.kind: "peer"`) are marked `agent`, and task notifications are not read.
- **Turn times:** The model receives turn times in this PC's local time with the UTC offset (for example `2026-11-04 16:50:45 +09:00`), and a quotation keeps the day it was said.
- **Project ID:** Committing `{"project":"stable-id"}` in an optional `.lore.json` file at the repository root makes every PC use the same memory even if checkout folder names differ. Using the existing name as the ID keeps the existing memory path. Without the file, the repository folder name is used as before. An invalid ID file is reported as a failure instead of falling back to the folder name.
- **New projects:** The first time approved candidates are written for a repository that has no memory folder, the app creates `projects/<name>/` and adds the qmd collection `project-<name>`.
- **Editing existing notes:** The model does not rewrite the whole body of an existing note; it sends only the places to change. The kinds are replace (replace a `find` copied verbatim from the body with new text), append to the end of a section, insert a new section, and restate a whole section. The text to replace and section headings must appear exactly once in the note body; otherwise the change is rejected and retried. Untouched text stays as it is. Only new notes are written in full. The frontmatter of an existing note is kept, except that `authority` is updated and `kind` is added only when missing. If the first line of the body is a `# ` line identical to the title, it is removed. A note whose text the model was not given cannot be edited.
- **Sources of a note:** The program, not the model, writes the `## Sources` list. Each quotation of the candidates that went into a note becomes one line: the day, who said it, and the words, for example `- 2026-11-17, user: "큐는 로컬. 싱크는 문서만."`. For a mark of the agent, its sentence is listed as the agent's words. `kind` and `authority` in the front matter are computed from the candidates as well: a note built only from lessons is a `lesson`; a note built from your own statements is a `user_decision`, from findings of the agent you did not confirm an `assistant_report`, and from proposals of the agent that you approved, from a mix, or when it differs from what the note said before, `mixed_evidence`. The model that writes the note is told the same, so that it never presents what the agent proposed as something you said.
- **Applying changes:** If someone edited a note after the changes to it were drafted, they are not applied and the batch is marked as failed; **Try again** drafts them against the note as it is now.
- **Automatic commits and review:** If the memory repository is a git repository (`<repository>/.git` exists), the app commits the changed files with the message "Record memory notes (today's date)" whenever a batch is written. Commits do not depend on review. The review window is for changes you did not decide one by one: notes changed by an automatic approval or by a cleanup. A note you approved a candidate into counts as reviewed, unless it already waited there with such a change; then it keeps waiting. If such notes (`common/`, `projects/`) changed on this PC since the last review, "Needs attention" shows the count as "Review N changed notes". Clicking "Review" opens the review window. The review window groups the changed notes by project (common first, then projects by name) together with what changed them, and shows each note line by line, side by side, as of the last review (left) and now (right). Within changed lines, changed words are highlighted, and runs of more than 6 unchanged lines are folded, leaving 2 lines before and after. Each note has a checkbox, and all are cleared when the window opens. Checkboxes on project headers and at the top of the list select a whole group. "Mark reviewed" marks only the checked notes as reviewed; unchecked notes stay for the next review. Files that are not notes, and notes received from other PCs, are not added to pending review. While the review window is open, no session is read, no batch is written and no sync starts; if work is in progress when it opens, the diff is shown after that work finishes. Work resumes when the window closes. Editing notes directly happens outside the app. Review is optional and not a condition for sync. Sync between PCs is described in the [sync guide](sync-review.md).
- **Recent activity:** The status screen shows the 30 most recent entries out of the recent activity kept in the app state DB (up to 500). Every row is two lines of the same height. A session that offered candidates is a "Candidates" row; a written batch is "n notes updated". A "Candidates" row says how many were offered then and how many of them still wait now ("3 candidates offered · 2 waiting", or "· all decided"); it opens the Candidates window only while some still wait. The second line shows the changed note names, how many candidates were offered, the reason nothing was offered, or an error on a single line; overflowing text is shown in full on hover. Clicking "n notes updated" opens a note list card over the list, from which you open notes. If there are notes to review, the card can also open the review window. Elapsed time and "m ago" are recalculated every 15 seconds. Clicking "Clear" next to "Recent activity" and confirming once more removes all recent activity. Memory notes, the queue, candidates and failed jobs are left untouched.
- **Bottom bar:** Shows the memory folder button and the sync status ("Synced 5m ago", "2 to check", "Sync needs attention", "Sync off", and so on). The button on the right syncs now, and opens the sync window when there are items to check or sync keeps failing. Reading sessions, writing notes and sync continue even when there are items to check. The last sync time changes only when an exchange with other PCs completes fully.
- **Saving settings:** Values on the settings screen apply as soon as you change them. Text fields save when you leave the field or press Enter, and show "Saved" next to the field. If the app rejects a value, it shows the reason and reverts the field to the saved value. The memory folder is not edited directly on the settings screen; use "Change…" to change it in the memory folder step of the integrations window.
- **Removing a note:** A note is removed only when you approved a candidate that ends it: the review showed that candidate as "Ends a note", with the note's title, its path and the passages that say what the note is about. The model may then remove the note, or edit it when part of it still holds. If the note was changed after you were shown it, for example by another approval or by a sync, it is not removed whole: only what the candidate ends is taken out, because you have not seen what was added. No other note is removed while approved candidates are written. The result and the recent activity show a removed note next to the changed ones.
- **Cleaning up notes:** Approved candidates are written a few at a time, so nothing in that flow notices that notes written months apart repeat each other, contradict each other, or describe something that no longer exists. A cleanup has the recording model read one folder at a time (a project's notes, or `common`) and tidy it: merge notes that say the same thing, remove notes whose subject is gone, take apart notes written around a session or ticket and put what is still needed into notes about its topic, and give notes file names that name their topic. While it cleans a project it also reads `common`, and moves there a correction to how the assistant works that would apply unchanged in any other project, saying which project and what kind of task the correction came from. A constraint or decision about the project itself stays in the project. A project cleanup adds to and edits `common` notes but removes none; choose `common` itself to tidy the shared notes. The cleanup waits for the work in progress, runs under the same lock as reading sessions, writing notes and sync, and applies its changes without asking: nobody has to approve each change. The result is one commit per folder, "Clean up memory notes (folder, date)", whose message lists each removed note with the reason and each moved note with its new path. The changed notes then wait in the review window. A cleanup changes only what the notes themselves show to be repeated, superseded or gone; it cannot look at code or sessions, so an open issue stays until a note says it was resolved. Folders with more than 80,000 characters of notes are cleaned in several requests, each of which sees the other notes by title and can ask for their text. Running a cleanup again on the same folder is safe and usually finds less.
- **The cleanup window:** Nobody has to decide which folder needs a cleanup. Lore counts, from the commits of the memory folder and without calling a model, how many notes of each folder are new or changed since that folder's last cleanup; a folder that was never cleaned counts all its notes. Once a folder has 10 or more, the tray window lists "N folders to clean up" under **Needs attention**, and **Open** shows the cleanup window (also reachable from **Settings → Memory & sync → Clean up notes**). The window lists those folders first, already checked, and **Clean up N folders** cleans them one after another, the shared folder last because cleaning a project can add to it. Any other folder can be checked too. While a run works, the list shows each folder as waiting, being cleaned, done or failed, the tray window shows which folder is being cleaned and how far the run is, and **Stop** drops the folders that still wait after the current one is finished. A finished run is one line in the recent activity. Choosing a folder shows what its last cleanup did: the summary, each removed note with the reason, each renamed or moved note, and the notes it changed or added. **Undo** reverts that cleanup with one commit, "Undo cleanup of memory notes (folder, date)", and refreshes the search index; when the same notes were changed again afterwards it refuses and leaves everything as it is. **Merge into another folder…** moves or removes every note of the chosen project folder into another one and cleans that one up, for example for the folder a project had under an earlier name.
- **Automatic cleanup:** **Settings → Memory & sync → Clean up automatically** is off by default. When it is on, Lore starts the same run by itself after approved candidates were written, once the queue is idle, for every folder that has 10 or more new or changed notes, and shares the result with the next sync. A folder whose cleanup failed is not started again by itself for a day. Each automatic cleanup is listed and can be undone like one started by hand.
- **Processing limits:** Under "Advanced" on the settings screen you can change the recording model timeout (default 600 seconds) and the qmd index and search timeout (default 900 seconds). They apply immediately to running calls once saved.

## CLI

```powershell
lore-cli doctor            # Diagnose paths and dependencies on this PC (does not create settings or the DB)
lore-cli index             # Register common/ and existing project collections, update the local qmd index
lore-cli project           # Show the memory project ID for the current repository
lore-cli status            # Queue status and failed jobs
lore-cli mark <decision|correction|lesson> "<sentences>" --by <user|agent> [--said "<the user's words>"]... [--common] [--updates <note> | --retires <note>] [--quote "<the note's words>"]... [--replaces <id>]   # Run by a session: prints the line Lore reads from the session file, with the mark's id; writes nothing
lore-cli mark cancel <id>  # Run by a session: withdraws one of its marks
lore-cli candidates        # List the candidates waiting for review
lore-cli candidates approve <id>...|all   # Approve candidates; `work` or the tray app then writes them into the notes
lore-cli candidates discard <id>...       # Discard candidates
lore-cli sync status       # Sync status and items to check
lore-cli sync now          # Commit, fetch, merge, push
lore-cli sync compare      # Compare notes changed on both PCs with the actual recording model
lore-cli retry <job ID>    # Requeue a failed or skipped job
lore-cli discard <job ID>  # Skip recording the failed segment of a failed job (the popover's "Skip")
lore-cli enqueue claude <source path>
lore-cli scan              # Queue sessions the hooks missed (the app does not do this automatically)
lore-cli cleanup           # List the note folders with how many notes changed since their last cleanup
lore-cli cleanup <folder> --dry-run   # Show what a cleanup would change, without changing a file
lore-cli cleanup <folder> [--absorb <folder>]   # Clean up and commit while the tray app is not running
lore-cli cleanup <folder> --undo   # Revert the folder's last cleanup while the tray app is not running
lore-cli work [--once]     # Read queued sessions and write approved candidates while the tray app is not running
lore-cli hooks             # Print hook connection status
lore-cli connect claude    # Connect to the global hook settings (backs up the previous file)
lore-cli disconnect claude # Remove lore hooks from the global hook settings (backs up the previous file)
```

`work`, `sync` and `index` refuse to run while the tray app is running (they use the same lock file).
